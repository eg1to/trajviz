## Detectores e métricas

Definição e correções dos detectores; o que entra nas métricas.

| Data | Decisão | Motivo | Alternativas descartadas |
| --- | --- | --- | --- |
| 19/11/2026 | `error` com exit code: ≠ 0 é erro, **exceto** exit 1 de `grep/egrep/rg/ag/diff/cmp/test/[/pgrep` (decidido pelo executável que define o exit code: último estágio do último segmento), exit −1 (OpenHands: processo ainda rodando) e, em passos `test`, qualquer exit ≠ 0 (isso é `test_fail`, não erro; só 126/127 ou "command not found" viram `error`). Sem exit code: padrões de texto; em passos read/search/explore/vcs (a saída é conteúdo de arquivo) só vale erro no estilo `ferramenta: …` na 1ª linha (`cat: x: No such file…`), nunca no meio do texto; editor: `No replacement was performed`, `did not appear verbatim`, `Multiple occurrences`, `Invalid …`, path inexistente | Evitar falso positivo em arquivos que citam `Traceback`/`SyntaxError`; grep sem match não é falha | Qualquer exit ≠ 0 |
| 19/11/2026 | `test_fail` / `test_pass` são flags separadas de `error` (pytest `N failed`, `FAILED`, `ERROR collecting`, `no tests ran`, unittest `FAILED (…)`, exit ≠ 0 → fail; `N passed`, `OK`, exit 0 → pass) | O dashboard conta ciclos edit → test e quantos terminaram em pass | Tratar teste falhando como erro |
| 19/11/2026 | `repeated` só conta a repetição de uma ação observadora/executora se **não houve edição** entre as duas (rodar o mesmo teste depois de editar não é repetição); passos `edit` idênticos contam sempre. A chave normaliza espaços, prefixos `/workspace/<repo>/`/`/testbed/`/`/app/`, `cd x &&`, view_range e hash de old_str/new_str | Refinamento do PLAN §6 ("mesma ação normalizada"): sem ele, `pytest` re-executado após cada edição seria sinalizado | Literal do PLAN |
| 19/11/2026 | `no_new_info`: (a) observação normalizada (sem rodapé de shell) idêntica a uma anterior de read/search/explore, com ≥ 20 chars; (b) releitura do mesmo arquivo/intervalo sem edição desde a leitura anterior (leitura inteira cobre intervalos); edições (inclusive via bash) invalidam | Equivalente automático de `unuseful_step_ids` | — |
| 19/11/2026 | `loop`: n-gramas (n = 2..4) de (categoria, alvo) repetidos ≥ 3 vezes seguidas **ou** ciclo edit → test_fail no mesmo arquivo ≥ 3 vezes; os intervalos ficam em `traj.meta["loops"]` e `flag_details["loop"]`; passos `message` entram na janela (uma sequência de mensagens sem ação é um laço real) | Spec da Fase 4 | Excluir `message` |
| 19/11/2026 | `message`, `keys` e `harness_protocol` aparecem à parte em `Metrics.effort` (contagem + idx) e **não** entram nas contagens por categoria/fase; `pct_total` (sobre todos os passos) e `pct_core` (sem eles) | Não inflar `think`/`other` (ex.: 445 mensagens numa trajetória) | Somar a think/other |
| 19/11/2026 | Backend: `loop` ignora passos `message` (loop do CTB: 20,8% → 3,8%) | Uma trajetória com 445 `message` seguidos distorcia a métrica | — |
| 19/11/2026 | `no_new_info` ajustado após auditoria (`results/audit_no_new_info.md`): 16/20 falsos positivos (80%) no SWE-smith → cobertura exige intervalo legível (inclui `view_range` em string), intervalo ⊂ intervalo já lido (ou igual), leitura inteira só cobre se não for abreviada (`<NOTE>This file is too large…`) nem truncada; observações de erro e "sem saída" não contam. Marcados no SWE-smith: 12,6% → 2,8%; nova amostra de 20: 0 falsos positivos | Spec: ajustar se > 25% falsos positivos | Manter a regra |
| 19/11/2026 | `test_fail` segue os códigos de saída do **pytest**: 1 = `test_fail`; 0 = `test_pass`; **5 = sem flag de teste**; 2, 3, 4 e qualquer outro = `error` (a execução falhou: interrompida/erro de uso/coleta; 3 = erro interno e "outros" são extensão minha, não pedida); sem exit code, "Interrupted"/erro de uso → `error` e "no tests ran"/"collected 0 items" → sem flag. unittest, tox, make e demais executores mantêm a regra anterior (exit ≠ 0 = `test_fail`). Teste para cada código e para os 3 formatos de comando | Auditoria: 9 dos 10 casos duvidosos de `test_fail` eram exit 2/4/5 do pytest | Qualquer exit ≠ 0 |
| 19/11/2026 | `loop` exige o **mesmo alvo normalizado**: n-grama (2–4) de AÇÕES idênticas (ferramenta + comando + arquivo + intervalo + trecho editado) repetido ≥ 3 vezes seguidas, ou ciclo edit → test_fail no mesmo arquivo ≥ 3 vezes **com a mesma assinatura de erro** (ids `FAILED t::x` do pytest / `FAIL: test (mod.Class)` do unittest / linhas `E …` / fim da saída sem números). Passos sem alvo (`think`, `task_tracker`, `message`, `submit`, keys, harness) ficam fora. Edições em trechos diferentes do mesmo arquivo e leituras de intervalos diferentes deixam de contar | Auditoria: 7/20 falsos positivos (edição em lote, leituras de intervalos diferentes); custo: revocação contra o gabarito caiu para 0,4% (48 passos marcados no CTB) | Só exigir mesmo arquivo |
| 20/11/2026 | `pytest … \| cmd`: se o pytest está num pipe (fora de aspas e de `2>&1`), o exit code é ignorado e `test_fail`/`test_pass`/`error` vêm do texto da saída ("N failed", "N passed", "no tests ran", erro de uso/coleta); sem veredito no texto, sem flag. `\|\|` e `\|` entre aspas não contam como pipe. Teste para os 9 casos. **Exceção declarada** à regra de não ajustar por causa de auditoria: é correção de defeito apontado na rodada 2 (exit do `grep` no fim do pipe), não rótulo do gold | O exit code do pipe é o do último comando (`tail`/`grep`), não o do pytest.
